# 采样、分析和对照

## 收集什么

每轮记录以下条件，而不是只记录 FPS：

- 设备型号、系统、TapTap 版本、小游戏实际版本、构建模式、引擎版本；是否是临时注入或重新加载的构建。
- 物理画布、逻辑视口/DPR、帧率设置、地图/镜头、敌人数、移动和施法帧数、UI/加载状态。
- 调试日志、profiler、投屏等开关，充电与低电量模式、明显温升和采样先后次序。保持关键条件一致，不需要未经测量猜测温度。
- 不启用 profiler 的帧记录：实际绘制间隔、p50/p95/p99/max、尾部无帧时长、draw calls/triangles、引擎可读显存分配量。采集脚本本身也有小额开销，对照双方保持相同。
- 独立 JS/CPU profile 与必要源码；长时间观察和移动/战斗需要单列，不能用静止窗口推断。

采集脚本使用 `Director.EVENT_AFTER_DRAW` 与 `performance.now()`，固定容量上限 10000 帧。不会每帧查询 screen 或打印日志。快照阶段读一次尺寸和 DPR。它记录的是绘制回调节奏；不等于面板刷新率或系统合成器实际显示帧率。

输出放 `src/cocos/test-results/performance/<新目录>/`（通常被忽略），紧凑、可审阅的结论放 `docs/performance/`。保留源文件路径和命令、原始数据、统计口径、已确认与待验证项。不要保存登录凭据或完整存档。

## 如何判读

| 观察 | 下一步 | 不能直接推出 |
| --- | --- | --- |
| JS 栈集中在同步桥接、序列化或日志 | 查直接调用者、调用次数，尝试事件缓存/重复提交消除 | 整台手机 CPU 都被游戏占满 |
| 帧时间高但 JS profile 平缓 | 查渲染提交、GPU/合成与系统调度，使用设备支持的工具 | 必然是 GPU 瓶颈 |
| draw calls/triangles 增长 | 查批次切断、材质/纹理与可见对象，结合耗时 | 单凭三角形数能算 GPU 时间 |
| JS heap/纹理分配持续增长 | 相同操作往返，查引用释放、资源持有、生命周期监听 | 资源缓存占用就是泄漏 |
| 静止顺畅，移动/战斗卡顿 | 重现同一路线和技能，查寻路、对象创建、动画、动态 UI | 静止优化已经解决所有卡顿 |

WebKit 的 ScriptProfiler 栈统计是采样次数，inclusive 路径彼此重叠，百分比不能相加。先核对栈帧顺序再判断 leaf：2026-11-15 实测结构第一帧为原生叶子，最后为 RAF 根。不要从压缩函数名直接猜业务。

当前 TapTap iOS 运行时曾返回全部为 0 的 profile 时间戳。此时只报告采样计数及 CPU 读数分布，不换算耗时、不做逐帧时间对齐。脚本保留宿主 `hostMonotonic` 作为收到事件的时间；它不是设备实际执行时刻。CPUProfiler 的 100% 代表一个核，范围是选中 Inspector 目标，不是整个 TapTap 进程，更不是整机负载。CPU 监测可能比帧窗口略长，平均数不是时间加权结果。

`device.memoryStatus` 中 buffer/texture 是图形资源分配统计；它不是完整 GPU 驻留、JS heap 或 App 常驻内存。iOS 没有 GPU timer 扩展时标记缺失；需要更深设备指标可检查完整 Xcode/Instruments，但不能把仅安装 Command Line Tools 当作有 xctrace/devicectl。Android 可按需收集目标进程的 `adb shell dumpsys meminfo <实际包名或PID>`，先确认目标进程，并记录单位与宿主范围。

## 关联到源码

- 导出本次 `Debugger.scriptParsed` 并按返回的 scriptId 调用 `Debugger.getScriptSource`，ID 随会话变化。iOS 脚本 `--profile --sources` 自动保存来源索引；不要复用案例里的 2/7 等 ID。
- 有 source map 则核对对应构建的 map；没有时保存运行时脚本并定位列附近文本，与当前源代码比对，避免把旧包栈解释为已修改代码。
- 对本案例 WebKit 的 line/column，先用已知片段确认 1 基坐标。JavaScript 列通常按 UTF-16 code unit 计数；Python 使用 `split('\n')` 而非 `splitlines()`，按 `utf-16-le` 切列，防止中文、补充字符或 Unicode 行分隔符错位。

## A/B 与回归

A 为原始代码，B 只改变一个已知热点，然后恢复 A，检查条件是否一致。记录绝对值和差值，明确采样短、热状态随时间变化或角色状态不一致等限制；若变化过大，重新获取可比数据，不强行给出提升百分比。

临时替换函数或 getter 仅在用户任务需要定位时考虑，保存原始 descriptor/函数，设置恢复看门狗，用 finally 恢复并给出恢复证明。发布代码用正规适配层，不把诊断 patch 直接作为引擎改动提交。默认采集脚本不做这种替换。

源码优化后检查尺寸变化、回前台、场景销毁重进、音乐开关/暂停/恢复等实际受影响路径。复用 `npm run check` 与 `npm test`。本机已有测试会调用 `python`；macOS 只有 `python3` 时，将现有 venv 的 bin 加到本次命令 PATH，不改测试来绕过环境缺失。

重新打包时复用 `Build-TapTap.ps1` 的版本、资源准备、Creator 导出、转换、校验流程。它当前配置的编辑器路径是 Windows 路径；Mac 要沿项目已有 macOS 构建记录执行相同阶段，不照抄 Windows 路径，也不为了测帧率修改生成的版本文件。打包自动升 patch，不能用旧包号冒充新源码。扫描新包后先读取实际版本，再测。

交付时说明：改了什么，为什么是瓶颈，代码检查/模拟验证/真机采样分别完成到哪一步，哪些设备和场景尚待验证。没有 GPU/温度数据就不宣称已解决发热，没有加载新包就不宣称新包已通过真机验收。
